# 사회자 없는 마피아 (mxfia) 설계

- 작성일: 2026-11-04
- 상태: 사용자 검토 대기

## 1. 목표와 범위

### 1.1 목표

같은 장소에 모인 6~12명이 사회자 없이 마피아 게임을 한다. 호스트도 일반 플레이어로 참여하며, 호스트를 포함한 어떤 기기도 게임 중에 다른 사람의 역할을 알 수 없다.

첫 번째 성공 기준: 지인 모임에서 iPhone과 Android를 섞어 실제로 한 판을 끝까지 하고, 게임 후 검증이 "모든 기록 정상"으로 끝난다.

### 1.2 필수 조건

| 조건 | 내용 |
|---|---|
| 기종 무관 | 호스트와 게스트 모두 iPhone/Android 어느 쪽이든 가능, 섞여도 가능 |
| 서버 없음 | 직접 운영하는 게임 서버, Firebase 없음. 정적 페이지(github.io), 공용 시그널링 릴레이와 공용 STUN(연결 시작 때만)만 사용. 게임 데이터는 기기 간 직접 전송 |
| 설치 없음 | 웹앱. QR 또는 링크로 바로 참가 |
| 자동 사회자 | 진행, 타이머, 발표, 판정을 앱이 수행 |
| 호스트도 플레이어 | 호스트 기기는 공개 진행과 메시지 전달만 하고 비밀은 모름 |

### 1.3 보안 수준 (B: 정보 분산 + 게임 후 검증)

- 게임 중에는 어떤 기기도 전체 역할을 모른다. 호스트도 예외가 아니다.
- 정상 앱은 자기 역할과 규칙상 알아야 할 정보만 보여준다.
- 거짓말과 조작은 게임 중에 막지 못할 수 있지만, 게임 후 검증에서 반드시 드러난다.
- 개조한 앱이 게임 중에 알 수 있는 정보는 9.1절에 명시한다.

### 1.4 범위 밖 (첫 버전)

- 호스트 이전 (호스트 기기가 꺼지면 게임 종료)
- TURN 중계 서버 (직접 연결이 막히는 네트워크는 미지원)
- 특수 역할 (역할 정의는 데이터로 분리해 두어 이후 추가 가능)
- 섞기 정당성 증명 (9.2절 업그레이드 경로 참고)
- 오프라인 동작(PWA), 원격 플레이, 음성 채팅, 다국어 (한국어만)

## 2. 게임 규칙

| 항목 | 규칙 |
|---|---|
| 인원 | 6~12명 |
| 구성 | 6~8명: 마피아 2 / 9~12명: 마피아 3. 경찰 1, 의사 1, 나머지 시민 |
| 진행 | 첫날 밤 → 아침 발표 → 토론 → 투표 → 처형 발표 → 밤 (반복) |
| 밤: 마피아 | 동료의 선택이 실시간으로 보임. 시간이 끝나면 살아 있는 마피아들의 최다 선택 대상을 처형. 동점이면 마피아 비밀 기반 결정적 무작위. 아무도 고르지 않으면 처형 없음. 동료 마피아는 선택 불가 |
| 밤: 의사 | 1명 보호. 자기 자신 가능 |
| 밤: 경찰 | 1명 조사, 결과는 "마피아 / 마피아 아님". 자기 자신 불가 |
| 밤: 시민 | "의심 가는 사람" 선택 (게임 결과 화면에 표시). 조작은 다른 역할과 동일 |
| 투표 | 공개 투표. 시간 내 미투표는 기권. 최다 득표자 처형, 동점 또는 전원 기권이면 처형 없음 |
| 사망자 역할 | 공개하지 않음 |
| 승리 | 살아 있는 마피아 0명이면 시민 승리. 살아 있는 마피아 수 ≥ 나머지 생존자 수이면 마피아 승리 |
| 시간 | 호스트가 시작 전 설정. 기본값 토론 3분, 밤 30초, 투표 30초 |
| 사망자 | 관전 화면으로 전환, 발언 금지(오프라인 규칙). 기기는 게임 끝까지 접속 유지 |
| 경찰 결과 | 그날 밤에만 표시, 낮에는 다시 볼 수 없음 |
| 화면 공개 | 앱 안내 문구로 "폰 화면을 다른 사람에게 보여주지 않기" 규칙 안내 |

## 3. 전체 구조

```
┌──────────────────────────────────────────────┐
│ web/        화면 (React + TypeScript + Vite)  │
├──────────────────────────────────────────────┤
│ engine/     공개 게임 진행 (순수 TS)            │
│ protocol/   비밀 처리 (순수 TS)                │
├──────────────────────────────────────────────┤
│ transport/  WebRTC DataChannel │ 메모리(테스트) │
│ signaling/  공용 릴레이        │ 메모리(테스트) │
└──────────────────────────────────────────────┘
```

### 3.1 모듈 책임

| 모듈 | 책임 | 의존 |
|---|---|---|
| `protocol/` | 키 생성, 암호화, 역할 배정, 밤 메시지 생성/해석, 게임 후 검증 | @noble 라이브러리만 |
| `engine/` | 게임 상태 머신, 규칙, 공개 로그 재생, 투표 집계, 승리 신호 처리 | `protocol/` |
| `transport/` | 피어 간 메시지 송수신 인터페이스와 구현 | 브라우저 WebRTC |
| `signaling/` | WebRTC 연결 정보 교환 인터페이스와 구현 | 공용 릴레이 클라이언트 |
| `web/` | 화면, 브라우저 저장소, Wake Lock, 음성 안내 | 위 전부 |

- `protocol/`과 `engine/`은 브라우저 API에 의존하지 않는다. Node에서 그대로 테스트한다.
- 의존 방향은 위 표의 아래쪽으로만 향한다. `engine/`과 `protocol/`은 `web/`, `transport/`, `signaling/`을 가져오지 않는다.

### 3.2 기술 선택

| 영역 | 선택 |
|---|---|
| 언어/빌드 | TypeScript, Vite, React |
| 암호 | @noble/curves (ristretto255, ed25519, x25519), @noble/hashes (SHA-256, HKDF), @noble/ciphers (XChaCha20-Poly1305) |
| 연결 | 브라우저 WebRTC DataChannel (ordered, reliable), 공용 STUN 서버 |
| 시그널링 | Nostr 공용 릴레이 3~4곳 동시 사용 (nostr-tools). 릴레이 목록은 12절 1단계에서 실측 후 선정. 불안정하면 MQTT 공용 브로커로 교체 |
| 저장 | IndexedDB (게임별 비밀 값과 로그) |
| 단위/시뮬레이션 테스트 | Vitest (Node) |
| E2E 테스트 | Playwright (PC 한 대에서 브라우저 컨텍스트 6~12개) |
| 배포 | GitHub Actions → GitHub Pages (`main` 푸시 시) |

### 3.3 메시지 흐름

- 모든 게스트는 호스트에게만 연결한다 (별형). 12명이면 연결 11개.
- 모든 메시지는 작성자가 서명한다 (게임별 Ed25519 키).
- 호스트는 받은 메시지에 순번을 붙여 모든 기기에 전달한다. 특정 상대에게 보내는 비밀 메시지도 암호문 상태로 모든 기기에 전달한다. 따라서 모든 기기가 같은 전체 로그를 갖는다.
- 각 기기는 로그를 순서대로 재생해 같은 공개 상태를 만든다.
- 각 기기는 로그의 누적 해시(SHA-256 체인)를 유지한다.
- 호스트가 직접 만드는 메시지(단계 전환, 타이머 시작/종료, 투표 마감)는 호스트 키로 서명한다.
- 타이머는 호스트 기준이다. 호스트가 단계 시작 메시지에 제한 시간을 담아 보내고, 종료 메시지로 마감한다. 기기 시계 차이는 영향이 없다.

## 4. 참가와 연결

### 4.1 방 만들기 (호스트)

1. 방 ID(128비트 무작위)와 호스트의 게임별 키(서명용 Ed25519, 시그널링용 X25519)를 만든다.
2. 링크와 QR을 표시한다.
   `https://<계정>.github.io/mxfia/#room=<방ID>&host=<호스트 X25519 공개 키>&sig=<호스트 Ed25519 공개 키>`
3. 방 정보는 URL fragment(`#` 뒤)에만 둔다. github.io 서버로 전송되지 않는다.
4. 시그널링 릴레이에서 방 ID 해시를 태그로 하는 메시지를 구독한다.

### 4.2 참가 (게스트)

1. 폰 기본 카메라로 QR을 찍거나 링크를 연다. 페이지 안 QR 스캐너는 없다 (카메라 권한 불필요).
2. 닉네임을 입력한다.
3. 게스트가 게임별 키(Ed25519, X25519)를 만들고, WebRTC offer를 호스트 X25519 공개 키로 암호화해 릴레이에 올린다 (Nostr ephemeral 이벤트, 릴레이 3~4곳 동시).
4. 호스트가 answer를 게스트 공개 키로 암호화해 회신한다. 릴레이에는 암호문만 지나간다.
5. DataChannel이 열리면 호스트가 링크의 Ed25519 공개 키로 서명한 핸드셰이크를 보내고, 게스트가 검증한다 (가짜 호스트 방지).
6. 게스트가 공개 키들과 닉네임을 등록한다.

### 4.3 대기실

- 참가 순서가 좌석 번호다. 호스트는 0번.
- 모든 기기가 참가자 목록과 각자의 공개 키를 받는다.
- 호스트는 시간 설정을 바꿀 수 있고, 인원에 따른 역할 구성이 표시된다.
- 6명 이상이면 호스트가 시작할 수 있다. 시작하면 명단이 확정되고 새 참가는 막힌다.
- 시작 전 호스트 배터리가 20% 미만이면 경고한다 (Battery Status API를 지원하는 브라우저에서만).

### 4.4 끊김과 재접속

- 게임 중 Wake Lock으로 화면 꺼짐을 막는다 (iOS 16.4+, 최신 Android Chrome).
- 5초 간격 heartbeat로 끊김을 감지한다.
- 게스트는 비밀 값과 로그를 IndexedDB에 저장한다. 새로고침하거나 탭이 백그라운드에서 돌아오면 같은 시그널링 방식으로 자동 재연결하고, 마지막 순번 이후 로그를 호스트에게서 받는다.
- 단계별 대기 정책은 8.2절 참고.

### 4.5 환경 대응

- 카카오톡 인앱 브라우저를 감지하면 "Safari 또는 Chrome으로 열기"를 안내한다.
- 핫스팟 사용 가능. 단, 시그널링 때문에 호스트 기기에 인터넷이 필요하다.
- 직접 연결이 불가능한 네트워크는 첫 버전에서 지원하지 않는다 (TURN 없음). 연결 실패 시 "같은 와이파이 또는 핫스팟으로 연결해 주세요"를 안내한다.

## 5. 역할 배정 프로토콜

### 5.1 표기

- 군: ristretto255, 생성원 `G`, 위수 `ℓ`, 항등원 `O`
- 좌석 `0..N-1`, 게임 ID `gid`
- ElGamal 암호화: `Enc(M; r) = (r·G, M + r·PK)`
- 역할 점: `R_role = hashToRistretto("mxfia/role/" + role)` (공개)

### 5.2 단계

**① 공동 키 생성**
- 각 기기 `i`: 비밀 스칼라 `x_i`, 공개 `X_i = x_i·G`, `x_i`에 대한 Schnorr 지식 증명(Fiat–Shamir, `gid`와 좌석 포함)을 서명해 공개한다.
- 모든 기기가 증명을 검증한다. 공동 공개 키 `PK = Σ X_i`.

**② 마피아 비밀 S 생성 (commit–reveal)**
- 각 기기 `i`: 무작위 `s_i`, `r_i`로 `E_i = Enc(s_i·G; r_i)`를 만들고, 먼저 `H(E_i)`를 공개한 뒤 모두의 커밋이 모이면 `E_i`를 공개한다. 커밋과 다르면 즉시 경고한다.
- `E_S = Σ E_i` (동형 합). `S = Σ s_i·G`이며 아무도 `S`를 모른다.

**③ 덱 구성 (공개, 결정적)**
- 인원 구성에 따라 카드 `N`장. 카드 `j` = (역할 칸 `A_j`, 비밀 칸 `B_j`).
- `A_j = (O, R_role_j)` (무작위성 0의 자명한 암호화, 섞기에서 재암호화됨)
- `B_j = E_S` (마피아 카드) / `(O, O)` (그 외)
- 카드 순서는 역할 이름순 고정.

**④ 섞기 (좌석 순서대로 순차)**
- 기기 `i`가 덱을 받아 무작위 순열 `π_i`를 적용하고, 각 카드의 두 칸을 각각 새 무작위 `ρ`로 재암호화한다: `(c1 + ρ·G, c2 + ρ·PK)`.
- 결과 덱을 서명해 공개한다. `π_i`와 모든 `ρ`는 IndexedDB에 저장한다 (게임 후 공개).
- 이 단계에서는 순서대로 한 명씩 진행하므로 해당 기기가 접속해 있어야 한다.

**⑤ 나눠주기 (동시)**
- 최종 덱의 `j`번째 카드는 좌석 `j`의 것이다.
- 각 기기 `i`는 자기 것이 아닌 모든 카드 `j`의 두 칸 각각에 대해 부분 해독값 `d = x_i·c1`과 Chaum–Pedersen 증명(DLEQ: `log_G X_i = log_{c1} d`)을 공개한다.
- 모든 기기가 증명을 검증한다. 틀리면 즉시 경고한다.
- 주인 `j`는 `M = c2 − Σ_{i≠j} d_i − x_j·c1`로 두 칸을 연다.
  - 역할 칸 `M`을 `R_role` 목록과 대조해 역할을 얻는다.
  - 마피아면 비밀 칸에서 `S`를 얻고 `K_mafia = HKDF(S, "mxfia/mafia/" + gid)`를 만든다. 아니면 비밀 칸은 `O`.

### 5.3 성질

- 한 명이라도 정직하게 섞으면 아무도 카드 배치를 모른다.
- 각 카드는 주인의 `x_j` 없이는 열 수 없다 (DDH 가정).
- 나눠주기의 부분 해독값은 증명이 있어 게임 중에 위조가 바로 드러난다.
- 같은 역할 카드끼리도 재암호화 때문에 구분되지 않는다.

## 6. 밤 프로토콜

밤 `n`마다 아래 3단계를 진행한다. 모든 단계에서 살아 있는 기기와 죽은 기기 모두가 같은 양, 같은 크기의 메시지를 보낸다 (트래픽만으로 역할이 드러나지 않게).

### 6.1 단계 N1: 선택 (밤 시간, 기본 30초)

- 모든 플레이어가 살아 있는 사람 중 한 명을 고른다. 화면 배치는 모든 역할이 같다.
- 모든 기기가 1초마다(틱) 고정 길이 `L` 바이트 블롭을 브로드캐스트한다. 마지막 틱에는 최종 선택을 담는다.
  - 살아 있는 마피아: `nonce(24) ‖ XChaCha20-Poly1305(K_mafia, nonce, {seat, n, tick, pick, final})`, 패딩으로 길이 `L` 고정
  - 그 외 (마피아 아님, 죽은 기기): 무작위 `L` 바이트
- 마피아 기기는 모든 블롭을 `K_mafia`로 열어본다. 열리는 블롭이 동료다. 첫째 밤 첫 틱에 서로를 알아보고, 이후 선택을 실시간으로 표시한다.
- 마피아가 아닌 기기와 호스트에게는 모든 블롭이 무작위로 보인다.

### 6.2 단계 N2: 행동 전달 (자동)

- 처형 대상: 살아 있는 마피아 기기 모두가 같은 방법으로 계산한다. 살아 있는 마피아들의 최종 선택 중 최다 득표, 동점이면 `HKDF(K_mafia, "tie/" + n)` 기반 결정적 선택, 선택 없음이면 처형 없음.
- 마피아 대표: 살아 있는 마피아 중 좌석 번호가 가장 작은 기기.
- 모든 기기 `i`가 다른 모든 기기 `j`에게 고정 길이 쌍별 암호문을 정확히 1통 보낸다.
  - 키: `k_ij = HKDF(X25519(i, j), "mxfia/night/" + gid + "/" + n + "/" + i + "→" + j)`
  - 내용 `{n, type}`. `type`은 다음 중 하나:
    - 마피아 대표 → 처형 대상: `KILL`
    - 의사 → 보호 대상: `SAVE` (자기 보호는 메시지 없이 로컬 처리)
    - 경찰 → 조사 대상: `QUERY`
    - 그 외 모두: `NONE`

### 6.3 단계 N3: 조사 응답 (자동)

- N2와 같은 방식으로 모든 기기가 서로 1통씩 보낸다 (고정 길이, 최대 내용 기준 패딩).
- `QUERY`를 받은 기기 `t`: 경찰에게 자기 역할 칸의 부분 해독값 `d = x_t·c1(A_t)`와 DLEQ 증명을 보낸다.
- 그 외: `NONE`.
- 경찰 기기는 증명을 검증하고, 나눠주기 때 공개된 다른 부분 해독값과 합쳐 역할 칸을 연 뒤 "마피아 / 마피아 아님"을 표시한다.
- 응답이 없거나 증명이 틀리면 경찰 화면에 "결과를 받지 못함"을 표시하고 게임 후 검증에서 보고한다.
- 역할 칸만 열리므로 경찰은 `S`를 얻지 못한다.

### 6.4 아침 발표

- 각 기기가 자기 운명을 판단한다: `KILL`을 받았고 `SAVE`를 받지 않았으면 (의사 자기 보호 포함) 사망.
- 모든 기기가 `{n, ALIVE | DEAD, logHash}`를 서명해 공개한다.
- 호스트 기기가 음성으로 "○○님이 사망했습니다" 또는 "아무도 죽지 않았습니다"를 안내한다.
- `logHash`가 서로 다르면 모두에게 "기록 불일치" 경고를 띄운다.

### 6.5 승리 판정

- 시점: 아침 발표 직후, 낮 처형 직후.
- 모든 기기가 `{checkpoint, CONTINUE | END_CITIZEN | END_MAFIA, logHash}`를 서명해 공개한다.
- 마피아가 아닌 기기는 항상 `CONTINUE`.
- 마피아 기기(생사 무관)는 첫째 밤에 확인한 마피아 명단으로 계산한다: 살아 있는 마피아 0명이면 `END_CITIZEN`, 살아 있는 마피아 수 ≥ 나머지 생존자 수이면 `END_MAFIA`, 아니면 `CONTINUE`.
- 유효한 `END`가 하나라도 있으면 게임이 끝난다. 서로 다른 `END`가 오면 경고하고 종료 후 검증한다.

## 7. 낮 진행

- 토론: 호스트 기준 타이머. 호스트가 "토론 종료"로 일찍 끝낼 수 있다 (공개 행동).
- 투표: 살아 있는 플레이어가 `{day, target | ABSTAIN}`을 서명해 보낸다. 마감 전까지 변경 가능하며, 현황은 실시간 공개된다. 호스트의 마감 메시지 이전의 마지막 투표가 유효하다.
- 집계는 모든 기기가 로그로 각자 수행한다. 결과 발표 후 승리 판정(6.5)으로 간다.

## 8. 게임 후 검증

### 8.1 절차

1. 게임 종료(승리 판정 또는 호스트의 "게임 끝내고 검증하기") 시 모든 기기가 게임별 비밀을 공개한다: `x_i`, `s_i`와 `r_i`, 섞기의 `π_i`와 모든 `ρ`, X25519 비밀 키.
2. 공개 제한 시간은 60초. 시간 내 공개하지 않은 기기는 "기록 공개 안 함"으로 표시하고, 그 기기에 의존하는 검증 항목은 "검증 불가"로 표시한다.
3. 각 기기가 다른 기기나 호스트를 믿지 않고 전체 로그를 처음부터 재계산한다.

| 검증 항목 | 잡아내는 조작 |
|---|---|
| 키 | 공개한 `x_i`가 `X_i`와 불일치 |
| 마피아 비밀 | `E_i`가 공개한 `s_i`, `r_i`와 불일치 |
| 섞기 | 섞는 척하며 카드를 바꿔치기 |
| 나눠주기 | 거짓 부분 해독값 |
| 마피아 블롭 | 마피아가 아닌 기기의 유효 블롭, 선택 기록 불일치 |
| 마피아 대표 | 대표가 아닌 기기의 `KILL`, 대상 계산 오류 |
| 밤 메시지 | 의사가 아닌 기기의 `SAVE`, 경찰이 아닌 기기의 `QUERY` |
| 조사 응답 | 응답 누락, 거짓 응답 |
| 아침 발표 | 처형당했는데 `ALIVE` 공개, 반대의 경우 |
| 승리 판정 | 끝났어야 할 게임에 `CONTINUE`, 잘못된 `END` |
| 로그 | 호스트의 메시지 누락·변조·기기별 다른 로그 전달 |

### 8.2 단계별 끊김 대기 정책

| 단계 | 정책 |
|---|---|
| 키 생성, 섞기, 나눠주기, 밤 N1~N3, 아침 발표, 승리 판정 | 모든 기기 필요. 돌아올 때까지 대기하며 "○○님을 기다리는 중" 표시 (누구를 기다리는지는 역할과 무관) |
| 토론, 투표 | 대기하지 않음. 미투표는 기권 |
| 언제든 | 호스트가 "게임 끝내고 검증하기" 가능 (공개 행동) |
| 호스트 기기 끊김 | 게스트는 재연결을 시도. 복구되지 않으면 게임 종료 (첫 버전) |

## 9. 한계와 업그레이드 경로

### 9.1 개조한 앱이 게임 중 알 수 있는 것

| 누가 | 알 수 있는 것 |
|---|---|
| 처형 대상 | 마피아 대표가 누구인지 (`KILL` 발신자) |
| 의사가 보호한 사람 | 의사가 누구인지 |
| 경찰 조사 대상 | 경찰이 누구인지 |

정상 앱은 이 정보를 표시하지 않는다. 호스트라서 추가로 알게 되는 정보는 없다.

### 9.2 개조한 앱이 게임 중 할 수 있고 게임 후에만 드러나는 조작

- 섞기에서 덱을 자기가 아는 암호문으로 바꿔치기하면 게임 중 모든 역할을 안다. 게임 후 검증에서 반드시 드러난다. 업그레이드 경로: 섞기마다 cut-and-choose 섞기 증명 추가 (보안 수준을 C 방향으로 높이는 첫 단계).
- 마피아가 아닌 기기가 가짜 `KILL`을 보내면 대상이 게임 중 사망 처리된다. 게임 후 드러난다.
- 마피아 기기가 승리 판정을 숨기면 게임이 이어진다. 호스트의 "게임 끝내고 검증하기"로 대응한다.

### 9.3 기타 위험

| 위험 | 대응 |
|---|---|
| 일부 네트워크에서 WebRTC 직접 연결 실패 | 1단계 기술 검증에서 조합별 확인. 필요 시 이후 TURN 검토 |
| 공용 릴레이 불안정 | 릴레이 3~4곳 동시 사용, 시그널링 인터페이스로 MQTT 교체 가능 |
| 모바일 브라우저 백그라운드 중단 | Wake Lock, 자동 재연결, IndexedDB 복구 |
| 카카오톡 인앱 브라우저 미지원 기능 | 감지 후 외부 브라우저 안내 |
| iOS 음성 자동 재생 제한 | "게임 시작" 터치 시 음성 활성화 |

```

    └─ 링크로 접속 ─▶ 닉네임 입력 ───┴─▶ 대기실
                                          │ 호스트 시작
                                          ▼
                       카드 섞는 중 ─▶ 내 역할 확인 (길게 눌러 보기)
                                          │
          ┌───────────────────────────────┘
          ▼
   밤 (선택) ─▶ 아침 발표 ─▶ 토론 ─▶ 투표 ─▶ 처형 발표 ─┐
          ▲                                          │
          └──────────────── 게임 계속 ───────────────┘
                                          │ 게임 끝
                                          ▼
                 검증 중 ─▶ 결과 (역할 공개 · 밤 타임라인 · 검증 결과)
```

| 화면 | 핵심 요소 |
|---|---|
| 홈 | 방 만들기, 닉네임, 화면 공개 금지 규칙 안내 |
| 방 설정 (호스트) | QR, 링크 복사, 참가자 목록, 역할 구성 표시, 시간 설정, 시작 버튼 (6명 이상) |
| 대기실 (게스트) | 참가자 목록, 내 좌석 |
| 카드 섞는 중 | 진행 상태 (단계, 기다리는 기기) |
| 내 역할 | 길게 누르는 동안만 표시. 마피아는 첫째 밤 이후 동료 표시. 낮에도 언제든 확인 가능 |
| 밤 | 어두운 테마, 역할별 문구(처형할 사람/지킬 사람/조사할 사람/의심 가는 사람), 같은 배치, 남은 시간. 마피아는 동료 선택 실시간 표시. 경찰은 밤 끝에 결과 |
| 아침/처형 발표 | 사망자 또는 "아무도 죽지 않았습니다", 음성 안내 (호스트 기기) |
| 토론 | 타이머, 생존자 목록, 호스트의 토론 종료 버튼 |
| 투표 | 생존자 목록, 실시간 투표 현황, 기권 |
| 관전 (사망자) | 공개 정보만 표시, 기기 켜두기 안내 |
| 결과 | 승리 팀, 전체 역할, 밤별 타임라인(마피아 선택·의사 보호·경찰 조사·시민 의심), 검증 결과(정상 또는 좌석·시점·내용별 위반) |

공개 음성 안내는 호스트 기기의 Web Speech API로 재생한다. 역할별 안내는 소리로 내지 않는다.

## 11. 테스트

### 11.1 프로토콜 단위 테스트 (Vitest, Node)

- 6~12명 각각에서 모두가 구성대로 역할을 받는다.
- 마피아 전원이 같은 `S`를 얻고, 마피아가 아니면 `O`를 얻는다.
- Schnorr, DLEQ 증명 생성/검증, 잘못된 증명 거부.
- 밤 행동 결과: 처형, 보호 성공, 자기 보호, 경찰 결과, 동점 처리, 선택 없음.
- 승리 판정 경계값.
- 8.1절 표의 조작 각각을 주입하고 검증이 정확한 좌석·시점·유형으로 잡아내는지 확인.

### 11.2 시뮬레이션 (Vitest, Node, 메모리 transport)

- 6~12명 가상 플레이어, 무작위 선택으로 수백 판 자동 진행. 모든 판이 종료되고 검증을 통과해야 한다.
- 트래픽 균일성: 호스트가 관찰하는 메시지의 개수와 크기 시퀀스가 역할 배정과 무관하게 동일해야 한다.
- 끊김 주입: 단계별 끊김/재접속 후 게임이 정상 종료된다.

### 11.3 E2E (Playwright)

- PC 한 대에서 브라우저 컨텍스트 6개 이상으로 실제 WebRTC와 메모리 또는 실제 시그널링으로 한 판 진행.

### 11.4 실기기

- 연결 조합: iPhone Safari ↔ Android Chrome (호스트 양방향), 섞인 게스트, 와이파이와 핫스팟, 카카오톡 인앱 브라우저.
- 12명 기준 섞기·나눠주기 소요 시간 측정 (목표: 10초 이내).
- 백그라운드 전환, 화면 잠금 후 재연결.

## 12. 만드는 순서

1. **웹 연결 기술 검증:** github.io에 최소 페이지를 배포한다. 호스트 QR → 게스트 링크 접속 → Nostr 시그널링 → DataChannel 핑. 같은 페이지에서 12명 기준 섞기·나눠주기 암호 연산 속도를 측정한다. 11.4절 조합을 시험한다. 결과에 따라 시그널링 방식이나 설계를 조정한다.
2. **프로토콜과 게임 진행:** `protocol/`, `engine/`을 Node에서 완성하고 11.1, 11.2절 테스트를 통과시킨다.
3. **화면:** `web/`을 붙인다.
4. **E2E:** 11.3절.
5. **실전:** 지인 모임에서 한 판.
